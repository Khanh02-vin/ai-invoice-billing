## Implementation plan: TASK 4 billing webhook idempotency/concurrency

1. **Harden SQLite connections in `src/billing/repository.py`**
   - Configure every file and in-memory connection with `timeout=10.0`, `check_same_thread=False` where needed, and `PRAGMA busy_timeout = 10000`.
   - Preserve existing schema/API compatibility and existing `webhook_events.id` primary-key semantics.

2. **Add an atomic repository webhook operation**
   - Implement `process_webhook_idempotent(event_id, provider, payload, event_type=..., side_effect=...)` or an equivalent repository-owned transaction boundary.
   - Start with `BEGIN IMMEDIATE`.
   - Insert the event with `ON CONFLICT(id) DO NOTHING` and inspect `rowcount`.
   - For duplicates, read the stored processed state, commit, and return an already-processed result without invoking side effects.
   - For new events, execute the subscription/entitlement side effect on the same connection/transaction, mark the event processed, then commit once.
   - Roll back on side-effect errors; preserve a separate failure update path that does not leave a half-applied transaction.
   - Avoid holding a transaction while relying on independent repository connections; use connection-aware internal helpers or a carefully scoped callback so all writes participate in the same transaction.

3. **Refactor `src/routers/billing.py`**
   - Remove the route-level `get_webhook_event` → `store_webhook_event` → apply → `mark_webhook_processed` sequence.
   - Call the new atomic repository operation directly and map its result to the existing response contract.
   - Keep provider signature validation and provider error handling unchanged.

4. **Extend `tests/test_billing.py`**
   - Add sequential duplicate delivery coverage asserting one side effect and an already-processed response.
   - Add concurrent duplicate delivery coverage using two threads and a file-backed SQLite database so separate connections exercise locking; assert no `database is locked` error and exactly one side effect.
   - Add failure/rollback coverage asserting the event and related billing changes are not left half-applied and the failure path is deterministic.
   - Keep current provider/signature/status tests passing.

5. **Validation/reporting**
   - Run targeted webhook/idempotency tests, full `tests/test_billing.py`, and then the full backend suite.
